# Spec: BBQlaw 2.0 — Expo app, OTA everything, self-identifying thermometers

Status: approved direction (Nav, 2026-11-26: Expo rewrite, opt-in upload, no
native 1.1). Revision 2 includes the Gemini 4 Neon review fixes.

`adapter-engine.md` is superseded **except** these sections, which stay
normative: §4 (UUID rules), §5 `match` rules and ranking, §7 (adapter host API:
calls, input checks, status rules, write allowlist, `setTarget`/`setBuzzer`
gate), §8 "Channels" (id derivation, lazy channel cards, device-level state,
remove-all-channels), §9 (golden vectors and their semantics), §10 (capture
flow, adapted here in §7). Its `JSContext`, `catalog.json`, fetch, test URL and
Pages Function parts are dropped.

## 1. Goal

1. All client logic and UI update over the air (OTA) without App Store review,
   as Caraid does with self-hosted Expo Updates.
2. The app identifies an unknown thermometer by trying the protocols it knows,
   scoring the results, and asking the user to confirm a reading. If nothing
   fits, the user can send a capture to us (opt-in). New protocols ship OTA.
3. **2.0.0 (App Store)** freezes the native shell and ships INT-11I-B parity +
   capture + upload. **The identify pipeline and family adapters ship as OTA
   updates after 2.0.0** (they are pure JS). The native package list in §4 is
   complete for both, so no second store build is needed for them.

First real target: a friend's ThermoMaven (protocol unknown). They install 2.0.0,
record a capture, and send it.

## 2. Hard requirements

- **R1 INT-11I-B parity** while the app runs (foreground or background after the
  JS runtime has started): same bytes (`adapter-engine.md` §9) and behaviour —
  auth, temperature, battery, docked, base target alarm, buzzer mute,
  watch-only, multi-probe, OpenClaw bridge, reconnect, target notification while
  backgrounded or locked. The one accepted gap is the cold background relaunch
  (§4.3).
- **R2 Same identity.** Bundle id `app.bbqlaw.ios`, team `866MN8FJSP`, iPhone only,
  iOS 17+. Restore identifier `app.bbqlaw.ios.central`.
- **R3 Passive capture never writes.** Identify trials write only after the user
  confirms (§6) and only an adapter's declared characteristics.
- **R4 A bad OTA never bricks.** Signed updates; expo-updates error recovery.
- **R5 No data leaves the phone without a tap** (except the existing OpenClaw
  bridge the user set up). No analytics, no accounts.
- **R6 Native surface is small, generic, and complete at 2.0.0** (§4), so OTA
  updates keep matching the runtime fingerprint.

### 4.2 `bbq-ble` (Swift, Expo Modules API)

A thin CoreBluetooth wrapper with no thermometer knowledge. Reuse proven code:
`BBQlaw/ThermometerManager.swift` on `main`, and the discovery barrier and
peripheral handling on branch `feat/adapter-engine` (commit `a4fa52f`,
`BBQlaw/ThermometerManager.swift`) — read with `git show a4fa52f:BBQlaw/ThermometerManager.swift`.

Ownership: an `ExpoAppDelegateSubscriber` creates the single `CBCentralManager`
(main queue, restore identifier `app.bbqlaw.ios.central`) inside
`application(_:didFinishLaunchingWithOptions:)`, so iOS can hand over restored
state even when no scene connects. The module instance uses that shared central.
The central retains every `CBPeripheral` it has seen or restored.

Functions:

| Function | Notes |
|---|---|
| `state()` | `poweredOn` / `poweredOff` / `unauthorized` / `unsupported` / `resetting` / `unknown` |
| `startScan()` / `stopScan()` | services nil, no duplicates |
| `connect(id)` | uses the retained peripheral, else `retrievePeripherals(withIdentifiers:)`; rejects if unknown |
| `cancel(id)` | |
| `discover(id)` | all services then all characteristics; resolves `[{service, chars:[{uuid, props[]}]}]` after every service reports (barrier; a failing service is logged and returned with `chars: []`) |
| `setNotify(id, service, char, on)` | resolves on `didUpdateNotificationStateFor`; rejects on error |
| `read(id, service, char)` | resolves bytes; rejects on error |
| `write(id, service, char, bytes, withResponse)` | without response resolves at once; with response resolves on `didWriteValueFor` |
| `restoredIds()` | peripherals iOS restored this launch |
| `setRestoreHint(text)` | stores the text shown in the §4.3 notification |
| `beginBackgroundWork(ms)` / `endBackgroundWork()` | JS-controlled `UIBackgroundTask`, capped at 25 s |

`service` may be `null` when the char UUID is unique on the peripheral; with a
duplicate UUID and `null` service, reject with `ambiguous_characteristic`.

Pending-promise rules: `didUpdateValueFor` resolves a pending `read` for that
characteristic first; otherwise it emits a `value` event. All pending promises
for a peripheral reject with `disconnected` on disconnect, and all pending
promises reject with `bluetooth_<state>` when the central leaves `poweredOn`.

Events (`EventEmitter`): `state`, `discovered {id, name|null, rssi, services[],
manufacturerData hex|null, serviceData{uuid: hex}}` (merge scan-response fields
natively before emitting), `connected {id}`, `disconnected {id, error|null}`,
`failedToConnect {id, error}`, `value {id, service, char, bytes, t}`,
`restored {ids[]}`.

Validation: every UUID from JS passes `adapter-engine.md` §4 checks before
`CBUUID(string:)`; invalid → reject `invalid_uuid`, never crash. Bytes from JS are
checked 0–255 integers.

Background execution: for every CoreBluetooth callback received while the app is
in the background, the module begins a `UIBackgroundTask` (if none is active) and
ends it 10 s after the last callback (cap 25 s, expiration handler ends it). This
keeps JS timers, `fetch`, and notification scheduling alive across BLE wakes.
JS additionally wraps OpenClaw pushes and auth retry sequences in
`beginBackgroundWork`/`endBackgroundWork`.

Event buffering: events before the first JS listener attaches are queued (cap
2,000) and flushed in order on attach.

### 4.3 Cold background relaunch (accepted gap)

Under Expo SDK 57's `UIScene` lifecycle, iOS can relaunch the app in the
background for Bluetooth restoration without starting React Native. JS (and
therefore adapters, alarms and the bridge) cannot run until the user opens the
app. Behaviour:
- The native central accepts restored state and keeps pending connections.
- If restored peripherals exist and no JS listener attaches within 5 s, post one
  local notification: title "Open BBQlaw to keep watching", body = the restore
  hint text set by JS (default "Your cook is no longer being watched.").
  Identifier `bbqlaw.restore`. Do not repeat it in the same launch.
- When JS starts, it reconnects and resumes normally.
- JS keeps the restore hint current: "Watching {probe names} · target {t}°".
- Do not attempt a headless React Native boot in 2.0.

## 5. Adapters (TypeScript)

```ts
export const adapter: AdapterDef = {
  id: 'inkbird-int-11i-b',
  name: 'INKBIRD INT-11I-B',
  family: 'inkbird-ff00',
  verified: true,
  match: [{ namePrefix: 'INT-11' }, { namePrefix: 'INKBIRD' }],
  signature: { service: 'FF00', chars: ['FF01', 'FF02', 'FF03'] },
  trialSafe: true,
  gatt: { notify: [...], read: ['2A19'], write: ['FF02'] },
  channels: 1,
  capabilities: ['food', 'battery', 'docked', 'deviceAlarm'],
  create: (host: AdapterHost) => ({ onReady, onNotify, setTarget, setBuzzer }),
};
```

- `src/engine/host.ts` implements `adapter-engine.md` §7 exactly: write
  allowlist, input checks (finite numbers, 0–255 integer bytes, channel range,
  `live` needs `foodF`, battery patch and clamp), the `setTarget`/`setBuzzer`
  gate (status `ready` + `deviceAlarm`), `after` with an injectable clock,
  `nowMs`, status mapping. The same `host.ts` runs in the app and in jest.
- `gatt` entries may be `"CHAR"` or `"SERVICE/CHAR"` when a UUID repeats across
  services. The session resolves each to `(service, char)` after `discover`.
- Port phase-1 `adapters/inkbird-int-11i-b/adapter.js` (on `feat/adapter-engine`,
  commit `844f48a`) with no byte changes. Its `vectors.json` runs under jest via a
  runner implementing `adapter-engine.md` §9 semantics against `create(host)`.
- A known device (advertisement match or remembered) whose `discover` result has
  none of its `gatt` chars → disconnect, forget the remembered mapping, and open
  the capture sheet with copy "BBQlaw can't read this thermometer yet."

## 6. Identify pipeline — **OTA phase, after 2.0.0**

Entry: the user taps an unmatched device in "Other Bluetooth devices".

1. Sheet "Find out how to read this thermometer". Copy: "BBQlaw will connect
   and try the thermometer protocols it knows. Only do this with your own
   thermometer." Buttons **Try protocols** and **Record capture instead**.
   No write happens before **Try protocols** (R3).
2. Connect, `discover`, build the fingerprint (below), look it up in
   `src/adapters/fingerprints.ts` (`hash → adapterId`).
3. Candidates: adapters with `trialSafe`, whose `signature.service` exists and
   whose `signature.chars` are all present in that service. Order: fingerprint
   hit, then verified, then larger signature.
4. Trial each candidate. The 30 s trial clock starts after `onReady()`. Score:
   - fail at once on any adapter exception or any reading outside −40…750 °F;
   - **live pass**: status `ready` reached and ≥ 2 `live` readings with
     consecutive steps < 15 °F;
   - **docked pass**: status `ready` and ≥ 1 `docked` reading → prompt "Take the
     probe out of the base" and wait up to 30 s more for a live pass.
   Between trials: cancel and reconnect.
5. On a live pass: "It reads **71.6°F** now. Does that match the thermometer's
   screen?" **Yes** → remember `deviceId → adapterId`, become a normal probe.
   **No** → next candidate.
6. No pass → capture (§7), with all attempts included.
7. Devices that failed are stored as `pending {deviceId, fingerprint, updateId}`.
   When the scan sheet shows a pending device and `Updates.updateId` differs from
   the stored one, show a row badge "New support — tap to retry". No background
   trials.

Fingerprint string (frozen; jest golden vector required):
- Lines `SERVICE/CHAR:props` for every discovered characteristic, excluding
  services `1800` and `1801`. UUIDs canonical (`adapter-engine.md` §4). `props`
  = the subset of `read,write,writeNoResponse,notify,indicate` present, in that
  order, joined by `+` (empty → `-`).
- Lines sorted by byte order, joined by `\n`, then `\nname:` + name prefix
  (advertised name up to the first digit, uppercased; empty if no name), then
  `\nmfr:` + manufacturer id as 4 lowercase hex digits (empty if < 2 bytes).
- Hash = SHA-256 lowercase hex (`expo-crypto`).

Family adapters (`verified: false`, OTA phase): `ibbq-fff0` and `thermopro-fff0`
from public open-source implementations, source URL and license cited in the
file, vectors built from that source. If bytes cannot be confirmed from a public
source, leave the family out and report it. Never guess bytes.

## 7. Capture and opt-in upload (ships in 2.0.0)

Flow = `adapter-engine.md` §10 (60 s; read each readable char then subscribe;
never write; ends on timer/stop/disconnect/dismiss/background; 5,000 events;
sanitised file name), in TypeScript over `bbq-ble` on the main central.
Differences:
- Values of `2A23` (System ID) and `2A25` (Serial Number) are recorded as
  `"redacted"`.
- JSON v2:

```json
{
  "bbqlawCapture": 2,
  "app": "2.0.0 (3)", "ota": "<updateId|embedded>", "ios": "26.1",
  "endedBy": "timer",
  "fingerprint": { "string": "...", "hash": "..." },
  "advertisement": { "name": null, "rssi": -60, "services": [], "manufacturerData": null, "serviceData": {} },
  "services": [ { "uuid": "FF00", "characteristics": [ { "uuid": "FF01", "props": ["notify"], "readValue": null, "readError": null } ] } ],
  "events": [ { "t": 1234, "service": "FF00", "char": "FF01", "hex": "02211f" } ],
  "identifyAttempts": [ { "adapterId": "...", "result": "fail|livePass|dockedPass|rejectedByUser", "reason": "...", "readings": [ { "t": 0, "state": "live", "foodF": 71.6 } ] } ]
}
```

- After capture: **Send to BBQlaw** and **Share file**. Copy under Send: "Sends
  this thermometer's Bluetooth name, layout and readings to BBQlaw. No account or
  location. Deleted after 90 days." Show the returned reference code.
- Restored peripherals that are not in persisted probes are cancelled once the
  central is `poweredOn` (this also cleans up an interrupted capture).

`relay/` changes:
- R2 binding `CAPTURES` → bucket `bbqlaw-captures` in `wrangler.toml`; 90-day
  lifecycle rule (document the `wrangler r2 bucket lifecycle` command in
  `relay/README.md`; Nav or the build runs it once).
- `POST /api/captures`: read the body as a stream, abort over 512 KB; parse
  JSON; require `bbqlawCapture === 2`; code = three words + 3 digits (reuse the
  relay's word list); store `captures/<code>.json` with `receivedAt` in
  `customMetadata`; return `{code}`. Per-IP limit 10 per hour: generalise the
  existing limiter to take a key prefix and window. Store no IP.
- `GET /api/captures` (list, newest first, 100) and `GET /api/captures/<code>`:
  require `authorization: Bearer <CAPTURES_ADMIN_TOKEN>` (Worker secret),
  compared as SHA-256 digests with `crypto.subtle.timingSafeEqual`. Validate
  `<code>` by characters (lowercase letters, digits, `-`; max 64). No wildcard
  CORS on these routes.
- `web/privacy/index.html`: one paragraph on opt-in captures and 90-day deletion.

## 8. OTA updates (port of Caraid, trimmed)

`app.config.ts`:
- `runtimeVersion: { policy: 'fingerprint' }`
- `updates: { url: 'https://updates.bbqlaw.app/manifest', checkAutomatically: 'ON_LOAD', fallbackToCacheTimeout: 0, codeSigningCertificate: './updates/certificate.pem', codeSigningMetadata: { keyid: 'root', alg: 'rsa-v1_5-sha256' }, requestHeaders: { 'expo-channel-name': CHANNEL } }`
  where `CHANNEL` = env `BBQLAW_CHANNEL` (`production` default, `preview` for
  TestFlight-only preview builds). No in-app channel switch.

App behaviour: on foreground, `checkForUpdateAsync` + `fetchUpdateAsync` in the
background; apply on the next cold start; never reload during a cook. Settings
shows the update id (first 8 chars) and date in `fg3`.

`updates-worker/` (Cloudflare Worker, route `updates.bbqlaw.app/*`, R2 bucket
`bbqlaw-updates`): port `caraid/apps/updates-host/src/app.ts` + `store.ts` and
adapt `protocol.test.ts` (vitest). Changes from Caraid: Workers runtime
(`crypto.randomUUID()`, no `node:` imports), R2 instead of GCS, channels
allowlisted (`production`, `preview`) from the request header instead of one
pinned channel, and `expo-server-defined-headers` not sent. Replace Caraid's
regex validators with character checks. Read-only; holds no keys.

`app/scripts/ota-keygen.ts`: generate the RSA key and self-signed certificate
with the exact OpenSSL extensions Caraid uses (`basicConstraints=critical,CA:FALSE`,
`keyUsage=critical,digitalSignature`, `extendedKeyUsage=critical,codeSigning`).
Private key → `~/.config/bbqlaw/ota-private-key.pem` (0600, never in the repo).

`app/scripts/publish-ota.ts` (port of `caraid/scripts/ota-updates.ts`, iOS only):
- Runtime version: resolve the fingerprint the way Caraid does for committed
  `ios/` (read `EXUpdates.bundle/fingerprint` from the built app, or
  `EXPO_UPDATES_WORKFLOW_OVERRIDE=managed npx expo-updates runtimeversion:resolve --platform ios`).
  Fail if it cannot resolve.
- `publish --channel preview|production`: `expo export --platform ios`, upload
  assets and launch bundle to R2 (`wrangler r2 object put --remote`), write a
  signed manifest, then move the channel pointer.
- `promote --from preview --to production`: copy pointer + signatures.
- `rollback --channel production --to <updateId>`: re-publish that update's
  assets under a **new** update id and fresh `createdAt`, re-signed.
- `embedded --channel production`: signed `rollBackToEmbedded` directive with a
  fresh commit time.

Caraid reference: `~/Developer/caraid/apps/updates-host/src/*`,
`~/Developer/caraid/scripts/ota-updates.ts`, `~/Developer/caraid/apps/mobile/app.config.ts`,
`~/Developer/caraid/infra/terraform/RUNBOOK_OTA_UPDATES.md`. Do not copy GCP,
Terraform, CMEK, Firebase or CI-identity parts.

## 10. Phases (each ends green)

1. **Skeleton**: Expo project, `bbq-ble`, theme, jest, `host.ts`, INT-11I-B
   adapter + vectors green, session manager, a debug screen (scan → connect →

## 11. Decisions (and how to reverse them)

- **Self-hosted OTA on Cloudflare**, same model as Caraid, no vendor account.
  Reverse: point `updates.url` at EAS (store build).
- **Thin custom BLE module**, no third-party BLE library.
- **Adapters live in the OTA bundle.**
- **Cold background relaunch shows a notification** instead of running JS
  (§4.3). Reverse: headless React Native boot in a later store build.
- **Identify ships OTA after 2.0.0**, so the store build carries less untested logic.
- **Preview channel = separate TestFlight build**, no in-app switch (App Review 2.5.2).
- **No 1.0 cook migration**; bridge links carry over when decodable.
- **Engine numbers** (30 s trials, 15 °F step, 512 KB, 10/hour, 90 days, 10 s
  background tail) are engine choices.

## 12. Build and test traps

- BLE does not work in the Simulator. Device checks are Nav's (phases 2 and 5).
- Tee long command output to a file, then read the file.
- No test over 5 s. No mocks of our own modules; adapter tests run real vectors
  through the real `host.ts`. jest never hits the network.
- `expo prebuild --clean` regenerates `ios/`; native changes only via config
  plugins or `modules/bbq-ble`.
- Any native change after 2.0.0 changes the runtime fingerprint and needs a store
  build. Keep §4.1 frozen.
- `expo-updates` with `ios/` committed stores `file:fingerprint` in `Expo.plist`;
  resolve the real value as §8 says.
- `wrangler r2 object put` needs `--remote`.
- No regex for validation or parsing (Nav's rule).
